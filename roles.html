Tech & implementation — languages and why we recommend them

This site is intentionally simple and lightweight. Below are recommended languages/technologies for the front-end and back-end and the reasoning behind each choice.

Front-end (what runs in the browser)

  • HTML5 — The semantic backbone of the site, accessible and SEO-friendly.
  • CSS3 (custom properties) — Used for theming (variables), responsive layout and visual polish. Lightweight, fast and easy to maintain.
  • JavaScript (ES6+) — Progressive enhancement only: small scripts for the year auto-update, reveal-on-scroll, and optional interactivity. Keeps initial load fast and the site remains usable without JavaScript.
  • Optional frameworks — If the society wants a richer interactive app, React or Vue can be used, but they add build complexity. For content-focused sites, they are overkill and slow down initial load.

Back-end / hosting (where the site is served from)

  • Static hosting (recommended) — GitHub Pages, Netlify or Vercel: zero-maintenance, free or low-cost, very fast via CDN. Forms can be handled via email links or serverless functions.
  • Serverless functions — For collecting applications or mailing-list signups, use lightweight serverless endpoints (Node.js or Python) provided by Netlify/Vercel/AWS Lambda. No server to maintain, scales automatically.
  • Full backend (optional) — If persistent data storage and authentication are needed, use Node.js with Express (JavaScript/TypeScript) or Python with Flask/FastAPI. Keep databases simple (PostgreSQL or SQLite).

Why these choices?

  • Accessibility & performance: a content-first, semantic HTML/CSS approach ensures pages load quickly on mobile and are usable by screen readers.
  • Low maintenance: static sites with optional serverless endpoints minimise ongoing operational work for student committees.
  • Modern JS only where it helps: small, modern scripts improve UX without the overhead of a full SPA, making the site friendly to sponsors and students who prioritise speed.
  • Easy to extend: if the society grows, moving to a small Node/Python backend and a lightweight database is straightforward — the front-end can remain the same and call RESTful APIs.
